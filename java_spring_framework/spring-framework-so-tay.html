Mạch kiến thứcSpring Core là phần nền của toàn bộ tài liệu. Ta đi theo thứ tự: IoC giải thích vì sao Spring quản lý object → Container là nơi thực hiện việc đó → Bean là object do Container quản lý → Dependency Injection (DI) là cách đưa dependency vào bean → component scan giúp Spring tìm bean → sau đó mới sang AOP và JdbcTemplate.

Phần 1 Tier 1 — bắt buộc

Inversion of Control

Bắt đầu từ khái niệmIoC là ý tưởng lớn nhất cần hiểu trước. Spring không chỉ cung cấp một loạt annotation; điểm cốt lõi là quyền tạo và kết nối object được chuyển từ code ứng dụng sang Container. DI là cách Spring hiện thực IoC trong phần dependency.

IoC là một trong những ý tưởng nền tảng của Spring. Hiểu được IoC sẽ giúp bạn hiểu vì sao Spring có Container, Bean và Dependency Injection.

1.1 · Khái niệm IoC

Inversion of Control (IoC), hay đảo ngược quyền kiểm soát, là nguyên tắc trong đó code của ứng dụng không còn tự quyết định toàn bộ việc tạo và kết nối các object. Một phần trách nhiệm này được chuyển cho framework.

Hiểu đơn giản

Thay vì một class tự new dependency mà nó cần, class chỉ khai báo “tôi cần object này”. Spring Container sẽ tạo object và đưa dependency vào cho nó.

Lợi ích:

  • Giảm coupling giữa các thành phần.
  • Dễ thay implementation mà không phải sửa code nghiệp vụ.
  • Class tập trung vào nhiệm vụ của nó thay vì lo tạo và tìm dependency.

Trong Spring: IoC Container quản lý các bean và dependency giữa chúng. Dependency Injection (DI) là cách phổ biến Spring dùng để hiện thực IoC.

Lợi ích của IoC

  • Giảm phụ thuộc chặt: các thành phần không cần tự tạo những dependency mà chúng sử dụng.
  • Dễ thay đổi và mở rộng: có thể thay implementation mà không phải sửa code nghiệp vụ.
  • Dễ kiểm thử: dependency có thể truyền từ bên ngoài, nên test có thể thay bằng implementation giả.
  • Tập trung vào nghiệp vụ: class tập trung vào việc nó cần làm thay vì kiêm luôn việc khởi tạo và lắp ráp các object khác.

IoC trong Spring

Trong Spring, IoC Container là thành phần chịu trách nhiệm tạo và quản lý các bean. Bạn khai báo bean và dependency giữa chúng; Container lo việc khởi tạo và kết nối chúng.

IoC trong Spring còn thể hiện ở cách framework gọi code của bạn. Ví dụ với ứng dụng web, bạn không tự viết vòng lặp để nhận HTTP request rồi tìm controller tương ứng. Spring nhận request, xác định handler phù hợp và gọi method controller mà bạn đã khai báo.

IoC và DI

IoC là khái niệm rộng. Dependency Injection (DI) là một cách cụ thể để thực hiện IoC: dependency được tạo ở bên ngoài rồi truyền vào object thay vì object tự tạo dependency đó.

1.2 · Vấn đề

Có một service in câu hỏi ra màn hình. Nó cần một thứ biết sinh câu hỏi:

code chưa dùng IoC 
public class SpringQuizMaster {
 public String popQuestion() { return "Are you new to Spring?"; }
}

public class QuizMasterService {

 private SpringQuizMaster quizMaster = new SpringQuizMaster(); // ★ chỗ này

 public void askQuestion() {
 System.out.println(quizMaster.popQuestion());
 }
}

Đoạn này chạy đúng. Vấn đề không phải nó sai, mà là nó cứng. Ba hệ quả cụ thể:

  • Không đổi được. Sếp bảo đổi sang StrutsQuizMaster → phải sửa file QuizMasterService.java rồi biên dịch lại. Một class đáng lẽ không liên quan gì tới chuyện đó.
  • Không test được. Muốn viết unit test cho askQuestion() mà không đụng tới SpringQuizMaster thật? Không có cách nào chen vào. Object đó được tạo bên trong, khoá kín.
  • Không tái dùng được. Service này vĩnh viễn gắn với một implementation. Ngữ cảnh khác cần bản khác thì phải copy cả class ra sửa.
Cách nhìn

Gốc rễ của cả ba là một điều: QuizMasterService đang làm hai việc — vừa lo nghiệp vụ (in câu hỏi), vừa lo quyết định dùng implementation nào. Việc thứ hai không phải trách nhiệm của nó.

1.3 · Bước 1 — tách interface

Trước hết, nói rõ “tôi cần một thứ biết popQuestion()”, không nói “tôi cần đúng class này”:

public interface QuizMaster {
 String popQuestion();
}

public class SpringQuizMaster implements QuizMaster { ... }
public class StrutsQuizMaster implements QuizMaster { ... }

Đây mới là bước chuẩn bị. Bản thân nó chưa giải quyết vấn đề gì — nếu vẫn new SpringQuizMaster() bên trong thì vẫn cứng y nguyên.

1.4 · Bước 2 — thôi tự tạo, nhận từ ngoài

đây chính là chỗ “đảo ngược” 
public class QuizMasterService {

 private final QuizMaster quizMaster; // chỉ khai KIỂU, không khai class cụ thể

 public QuizMasterService(QuizMaster quizMaster) { // ai đưa vào thì tôi dùng cái đó
 this.quizMaster = quizMaster;
 }

 public void askQuestion() {
 System.out.println(quizMaster.popQuestion());
 }
}

Ba vấn đề ở 1.1 biến mất cùng lúc:

// đổi implementation: sửa chỗ gọi, không sửa QuizMasterService
new QuizMasterService(new StrutsQuizMaster());

// test: cắm bản giả vào, không cần DB, không cần Spring
QuizMaster fake = () -> "câu hỏi giả";
new QuizMasterService(fake).askQuestion();

Chữ “Inversion” nằm ở đây: quyền quyết định “dùng cái nào” bị lấy ra khỏi class và đẩy lên trên.

1.5 · Bước 3 — nhưng “bên ngoài” là ai?

Đẩy quyết định lên trên thì phải có ai đó ở trên nhận. Với ba class thì bạn tự làm được:

tự lắp bằng tay 
public static void main(String[] args) {

 // bạn tự quyết dùng implementation nào
 QuizMaster qm = new SpringQuizMaster();

 // tự lắp, đúng thứ tự
 QuizMasterService service = new QuizMasterService(qm);

 service.askQuestion();
}

Ba class thì nhìn còn dễ chịu. Dự án thật thì không:

  • Không phải 3 class mà vài trăm class, chuỗi phụ thuộc sâu bốn năm tầng
  • Nhiều nơi phải dùng chung một instance (một connection pool, không phải mỗi chỗ một cái) → bạn phải tự nhớ đã tạo cái gì, truyền đi đâu
  • Thêm một dependency vào class ở tầng đáy → phải sửa dây chuyền ngược lên tận main()
  • Đổi implementation → phải tìm đúng dòng trong cái main() dài mấy trăm dòng

Đó là việc của container. Bạn khai báo “có những class này, chúng cần nhau thế này”, container lo phần lắp ráp — và mục tiếp theo cho bạn xem nó làm việc đó ra sao, bằng một project chạy được đầy đủ.

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController // ④
public class QuizController {

 this.service = service;
 }

 @GetMapping("/quiz")
 public String quiz() {
 return service.askQuestion();
 }
}

1.7 · Điều gì xảy ra khi ứng dụng khởi động

Sáu bước, theo đúng thứ tự này:

  • 1
    main() chạy, gọi SpringApplication.run(DemoApplication.class, args). Từ đây Spring cầm lái.
  • 2
    Tạo container (ApplicationContext). Lúc này nó rỗng.
  • 3
    Quét package. Vì @SpringBootApplication ⑥ nằm ở com.example.demo, Spring quét package đó và mọi package con, tìm class có annotation stereotype.
  • 4
    Ghi vào sổ đăng ký — mới chỉ là bản kê: tên bean, kiểu, cần những gì. Chưa tạo object nào.
  • 5
    Tạo object và lắp ráp, tự sắp thứ tự theo phụ thuộc.
  • 6
    Khởi động Tomcat, đăng ký /quiz vào QuizController. App sẵn sàng nhận request.

Bước 3 tìm được ba class:

SpringQuizMaster ← có @Component ①
QuizMasterService ← có @Service ②
QuizController ← có @RestController ④

Java có khả năng tên là reflection — chương trình tự soi chính mình lúc đang chạy: liệt kê class, đọc annotation trên chúng, xem constructor cần tham số gì, và tạo object mà chỉ cần đọc hiểu new trong code. Spring làm hai việc:

Hollywood Principle

Nguyên tắc này có tên riêng: “Don't call us, we'll call you.”

Code thư viện thì bạn gọi nó. Code framework thì nó gọi bạn. Đó là khác biệt duy nhất giữa hai thứ — và cũng chính là nghĩa gốc của chữ Inversion trong Inversion of Control: luồng thiết lập bị đảo ngược.

Bên frontend bạn đã quen rồi mà chưa gọi tên: viết onClick={handleClick} trong React, bạn không gọi handleClick() — bạn đưa nó cho React, và React gọi khi cần.

Phần 3 Tier 1 — bắt buộc

Bean

Mối liên hệ với ContainerBean không phải một loại class đặc biệt. Bean là một object được Spring IoC Container tạo, lắp ráp và quản lý. Vì vậy, khi gặp @Service, @Repository hoặc @Bean, hãy nghĩ ngay: “object này sẽ được đưa vào Container để Spring quản lý”.

Định nghĩa thì một dòng. Phần thật sự quan trọng là scope và hệ quả của nó — mục 3.4.

3.5 · Vòng đời bean bổ sung

@Service
public class CacheService {

Đừng đặt logic khởi tạo cần dependency vào constructor — lúc constructor chạy, các dependency khác có thể chưa sẵn sàng. Đó là lý do @PostConstruct tồn tại.

Lưu ý nhỏ: bean prototype không gọi @PreDestroy. Container giao bean xong là buông, không theo dõi nữa.

Dừng lại kiểm tra — khi nào dùng @Bean thay vì @Component?

Khi class đó không phải của bạn nên không thêm annotation vào được (PasswordEncoder, RestTemplate, ModelMapper), hoặc khi việc tạo object cần logic — đọc cấu hình, đăng ký module, chọn implementation theo điều kiện.

Dừng lại kiểm tra — vì sao không được để private int counter trong @Service?

Vì @Service là singleton: chỉ có một object dùng chung cho mọi request, và nhiều thread chạy song song trên nó. Hai request cùng tăng counter sẽ tranh nhau, giá trị sai mà không có lỗi nào được ném ra. Cần đếm thì dùng AtomicInteger, hoặc tốt hơn là để dữ liệu ở nơi nó thuộc về — database.

Phần 4 Tier 1 — bắt buộc

Dependency Injection

Mối liên hệ với IoCIoC nói rằng quyền quyết định dependency được đưa ra ngoài class. DI trả lời câu hỏi “đưa dependency vào class bằng cách nào?”. Trong Spring, constructor injection là cách thường dùng nhất vì dependency được thể hiện rõ ngay ở constructor.

4.2 · Vì sao constructor injection

Bốn lý do, xếp theo mức độ quan trọng thực tế:

  • Bất biến. Field khai được final — sau khi object tạo xong không ai đổi được dependency của nó nữa.
  • Hỏng sớm. Thiếu bean thì app không khởi động, kèm thông báo rõ ràng. Với field injection, app lên bình thường rồi NullPointerException lúc user bấm nút.
  • Test được bằng Java thuần. Không cần khung Spring, không cần annotation gì:
@Test
void traVeUserKhiTonTai() {
 UserRepository fakeRepo = new InMemoryUserRepository();
 UserService service = new UserService(fakeRepo); // ← chỉ được với constructor

 assertEquals("minh", service.getById(1L).getName());
}
  • Lộ ra class đang phình to. Constructor có tám tham số thì ai nhìn cũng thấy class này ôm quá nhiều việc. Với field injection, tám dòng @Autowired nằm rải rác nhìn vẫn thấy sạch sẽ — vấn đề bị che đi.
Bỏ được @Autowired

Từ Spring 4.3, class chỉ có một constructor thì không cần @Autowired — Spring tự hiểu. Code thật trong dự án trông như thế này, và đây là kiểu bạn nên viết:

@Service
public class OrderService {

 private final OrderRepository orderRepo;
 private final PaymentGateway payment;

 public OrderService(OrderRepository orderRepo, PaymentGateway payment) {
 this.orderRepo = orderRepo;
 this.payment = payment;
 }
}

Dùng Lombok thì rút gọn thêm được bằng @RequiredArgsConstructor — nó tự sinh constructor cho mọi field final. Nhiều dự án Sun* dùng cách này.

4.3 · Khi có nhiều bean cùng kiểu

@Autowired khớp theo kiểu. Hai class cùng implement một interface là container không biết chọn cái nào:

@Component class MomoGateway implements PaymentGateway { }

@Component
@Primary

// ② @Qualifier — chọn đích danh tại chỗ inject, dùng khi mỗi nơi cần một bản khác

Chuỗi ưu tiên khi khớp bean: kiểu → @Qualifier nếu có → @Primary nếu có → tên tham số. Vì có bước cuối cùng đó nên đôi khi đặt tên tham số trùng tên bean cũng chạy — nhưng đừng dựa vào nó, vì tên tham số có thể bị xoá khi biên dịch.

4.4 · Inject cả nhóm bean bổ sung

Nhiều bean cùng kiểu không phải lúc nào cũng là vấn đề — đôi khi đó chính là cái bạn muốn:

@Service
public class NotificationService {

 private final List<NotificationChannel> channels; // Spring cắm TẤT CẢ bean kiểu này

 public NotificationService(List<NotificationChannel> channels) {
 this.channels = channels;
 }

 channels.forEach(c -> c.send(message));
 }
}

// Thêm SmsChannel mới? Chỉ cần gắn @Component. NotificationService không đổi một dòng.

Đây là cách cài Strategy pattern rất gọn, và là ví dụ rõ nhất cho việc IoC giúp code “mở để mở rộng, đóng để sửa đổi”.

4.5 · Phụ thuộc vòng tròn

@Service class A { A(B b) { } }
@Service class B { B(A a) { } }

// → app không khởi động: The dependencies of some of the beans form a cycle

Từ Spring Boot 2.6, phụ thuộc vòng tròn bị cấm mặc định. Có thể bật lại bằng cấu hình, nhưng đừng — nó gần như luôn là dấu hiệu chia trách nhiệm sai. Cách chữa đúng là tách phần dùng chung của A và B ra một class thứ ba.

Dừng lại kiểm tra — vì sao field injection khó test?

Vì không có đường nào đưa dependency vào từ bên ngoài: không có constructor nhận nó, không có setter. Test buộc phải khởi động cả Spring context, hoặc dùng reflection để gán giá trị vào field private. Cả hai đều chậm và rườm rà hơn hẳn new UserService(fakeRepo).

Dừng lại kiểm tra — @Primary và @Qualifier, khi nào dùng cái nào?

@Primary khi có một lựa chọn là mặc định hợp lý cho hầu hết nơi dùng — đặt một lần trên bean đó. @Qualifier khi mỗi nơi cần một bản khác nhau — đặt tại từng chỗ inject. Hai cái dùng chung được: @Primary lo số đông, @Qualifier lo ngoại lệ.

Phần 5 Tier 1 — bắt buộc

Annotation lõi và component scan

Mối liên hệ với Bean và DICác stereotype như @Component, @Service và @Repository giúp Spring phát hiện class để đăng ký thành bean. Sau khi bean được đăng ký, Container mới có thể inject bean đó vào nơi cần dùng.

Bộ annotation bạn gõ hằng ngày, và một cái bẫy về package khiến người mới mất cả buổi.

@Repository dịch exception nghĩa là gì

JDBC ném SQLException, Hibernate ném exception riêng của nó. @Repository bọc lại và chuyển hết thành cây DataAccessException của Spring — unchecked, và có tên rõ nghĩa như DuplicateKeyException, EmptyResultDataAccessException. Nhờ đó tầng Service bắt lỗi mà không cần biết bên dưới là JDBC hay JPA.

5.3 · @Configuration

Đánh dấu class là nguồn định nghĩa bean. Các method @Bean bên trong sẽ được container gọi để lấy object.

@Configuration
public class AppConfig {

 @Bean
 public PasswordEncoder passwordEncoder() {
 return new BCryptPasswordEncoder();
 }

 @Bean
 public UserValidator userValidator(UserRepository repo) { // tham số cũng được inject
 return new UserValidator(repo);
 }
}

Một chi tiết hay được hỏi: gọi passwordEncoder() hai lần bên trong class @Configuration vẫn trả về cùng một object, không tạo mới. Spring can thiệp vào class này (bằng proxy) để giữ đúng ngữ nghĩa singleton.

Dừng lại kiểm tra — @Service và @Component khác nhau thế nào?

Về kỹ thuật thì không khác gì — @Service chính là @Component được đặt tên lại. Khác biệt nằm ở ý nghĩa: nó nói cho người đọc code biết class này thuộc tầng nghiệp vụ. Đây là câu hỏi bẫy hay gặp, và trả lời “@Service mạnh hơn” là sai.

Hai cái thật sự có thêm hành vi là @Repository (dịch exception) và @Controller (Spring MVC quét tìm handler).

Phần 7

Bài tập ôn tập

Bốn bài tăng dần, làm trong một project Spring Boot trắng tạo từ start.spring.io (chỉ cần dependency Spring Web). Gợi ý nằm trong phần mở ra được — thử tự làm trước.

Bài 1. Tạo GreetingService trả về một câu chào, inject nó vào một controller, chạy và gọi thử.

Mục tiêu: quen vòng lặp cơ bản — gắn annotation, nhận qua constructor, chạy được.

@Service
public class GreetingService {
 public String greet(String name) { return "Xin chào, " + name; }
}

@RestController
public class GreetingController {
 private final GreetingService service;

 public GreetingController(GreetingService service) { this.service = service; }

 @GetMapping("/greet")
 public String greet(@RequestParam String name) { return service.greet(name); }
}
Bài 2. Tạo interface MessageFormatter với hai implementation (PlainFormatter, UpperCaseFormatter). Chạy thử — chuyện gì xảy ra? Sau đó sửa cho chạy được bằng hai cách khác nhau.

App không khởi động, báo NoUniqueBeanDefinitionException: expected single matching bean but found 2. Đây là bài quan trọng nhất trong bốn bài — hãy đọc kỹ thông báo lỗi, vì bạn sẽ gặp lại nó rất nhiều.

Cách 1: gắn @Primary lên PlainFormatter. Cách 2: bỏ @Primary, dùng @Qualifier("upperCaseFormatter") ở chỗ inject. Thử cả hai để thấy khác biệt: @Primary đặt một lần ở phía bean, @Qualifier đặt ở từng nơi dùng.

Bài 3. Tự chứng minh chuyện scope: tạo một bean có biến đếm, gọi tăng hai lần từ hai chỗ khác nhau, in ra. Rồi đổi sang @Scope("prototype") và so kết quả.

Với singleton (mặc định), biến đếm cộng dồn — hai chỗ dùng chung một object. Với prototype, mỗi chỗ nhận một object riêng nên đếm luôn về 1.

Làm xong bài này, đọc lại mục 3.4 về vì sao không được để state trong field của @Service — bạn vừa tự tay tạo ra đúng tình huống đó.

Bài 4. Khai một @Bean trả về ObjectMapper đã cấu hình sẵn, inject vào service và dùng. Sau đó tự trả lời: vì sao không thể gắn @Component lên ObjectMapper?

Vì ObjectMapper là class của thư viện Jackson — nó nằm trong file JAR, bạn không sửa được source để thêm annotation. Đó chính là lý do @Bean tồn tại.

Đây cũng là lúc nhìn lại: mọi @Bean bạn sẽ viết trong dự án thật đều rơi vào nhóm này — PasswordEncoder, RestTemplate, ModelMapper, ObjectMapper.

Phần 8

Ôn lại trước khi sang phần tiếp theo

Trả lời trôi chảy cả mười câu là xong Bài 1. Câu nào vấp thì quay lại đúng mục đó.

1. IoC là gì? Giải thích bằng ví dụ code trước và sau.

Quyền quyết định “dùng implementation nào” chuyển từ class sang bên ngoài. Trước: private QuizMaster qm = new SpringQuizMaster(); — class tự quyết. Sau: nhận qua constructor — ai gọi thì quyết. Xem mục 1.

2. IoC và DI khác nhau ở đâu?

IoC là nguyên tắc, DI là kỹ thuật thực hiện nguyên tắc đó. DI là cách phổ biến nhất để đạt IoC.

3. Bean là gì?

Object do container khởi tạo, lắp ráp và quản lý vòng đời. Không cần getter/setter — khác với JavaBean kiểu cũ.

4. Scope mặc định là gì, và vì sao điều đó ảnh hưởng tới cách viết @Service?

singleton — một object dùng chung cho mọi request, nhiều thread chạy song song trên nó. Vì vậy field chỉ để chứa dependency và cấu hình; dữ liệu thay đổi theo lời gọi phải là biến cục bộ. Xem mục 3.4.

5. Khi nào dùng @Component, khi nào @Bean?

Class của mình → @Component/@Service. Class của thư viện ngoài, hoặc cần logic khi tạo → @Bean trong @Configuration.

6. Ba kiểu injection, nên dùng cái nào và vì sao?

Constructor, setter, field. Dùng constructor: field final được, thiếu dependency là lỗi lúc khởi động, test bằng new không cần Spring, và constructor phình to thì lộ ngay class đang ôm quá nhiều việc.

7. Có hai bean cùng kiểu thì lỗi gì, chữa bằng gì?

NoUniqueBeanDefinitionException lúc khởi động. Chữa bằng @Primary (chọn mặc định, đặt ở bean) hoặc @Qualifier("tên") (chọn đích danh, đặt ở chỗ inject).

8. @Service, @Repository, @Component khác nhau thế nào?

Cả ba đều là bean. @Service chỉ khác @Component ở ý nghĩa. @Repository có thêm hành vi thật: dịch exception của JDBC/JPA sang DataAccessException.

9. Gắn @Service rồi mà Spring báo không tìm thấy bean — vì sao?

Khả năng cao nhất: class nằm ngoài cây package chứa class @SpringBootApplication, nên không được component scan. Chuyển class vào dưới package gốc. Xem mục 5.2.

10. Vì sao ApplicationContext khởi tạo bean sớm lại là điều tốt?

Vì cấu hình sai bị phát hiện lúc khởi động chứ không phải lúc người dùng bấm nút. App lên được nghĩa là toàn bộ sơ đồ phụ thuộc đã được kiểm tra xong.

Sang Bài 2 mang theo gì

Bài 2 nói về AOP, và nó xây thẳng lên hai thứ bạn vừa học: aspect cũng là một bean (nên vẫn cần @Component), và Spring áp advice bằng cách bọc bean của bạn trong một proxy. Nắm chắc “container quản object” thì phần proxy sẽ vào rất nhanh.

Bài 2 · Phần 1 Tier 1 — bắt buộc

Vấn đề — code lặp khắp nơi

Vì sao AOP xuất hiện sau IoC/DIIoC và DI giải quyết chuyện object nào được tạo và phụ thuộc vào object nào. AOP giải quyết một vấn đề khác: những logic như logging, transaction hoặc security xuất hiện ở nhiều nơi và dễ bị lặp. Vì vậy AOP là phần tiếp theo hợp lý sau khi đã hiểu cách Spring quản lý bean.

AOP nghe trừu tượng, nhưng bài toán nó giải thì rất cụ thể. Nội dung này đúng tình huống này.

Định nghĩa

AOP (Aspect Oriented Programming) là kiểu lập trình giúp tách các mối quan tâm xuyên suốt — cross-cutting concerns — ra khỏi logic chính của ứng dụng.

Những mối quan tâm đó gồm ghi nhật ký (logging), bảo mật (security), quản lý giao dịch (transaction), cache, đo hiệu năng. Thay vì lặp lại cùng một đoạn code ở mọi method, bạn định nghĩa nó một nơi duy nhất rồi để AOP “tiêm” vào đúng các vị trí cần thiết.

1.1 · Yêu cầu

Có class A với 5 method bắt đầu bằng m và 2 method bắt đầu bằng n. Yêu cầu: ghi log và gửi thông báo sau mỗi method bắt đầu bằng m.

class A {
 public void m1() {...}
 public void m2() {...}
 public void m3() {...}
 public void m4() {...}
 public void m5() {...}
 public void n1() {...}
 public void n2() {...}
}

1.2 · Làm theo cách thông thường

phải sửa 5 chỗ

 // 3 dòng nghiệp vụ thật sự
 log.info("m1 đã chạy"); // ← lặp
 notificationService.send(...); // ← lặp
}

public void m2() {
 // 3 dòng nghiệp vụ thật sự

// ... m3, m4, m5 y hệt

Ba vấn đề, và cái thứ ba mới là nghiêm trọng nhất:

  • Lặp. Cùng hai dòng đó ở năm chỗ. Dự án thật thì không phải 5 mà là 200 method.
  • Khó đổi. Muốn đổi định dạng log, hoặc thêm thời gian chạy vào? Sửa 200 chỗ.
  • Dễ quên. Tháng sau ai đó thêm m6() và quên hai dòng kia. Không có lỗi nào báo. Với log thì mất dữ liệu; với kiểm tra quyền thì đó là một lỗ hổng bảo mật.
Tên gọi của loại vấn đề này

Log, transaction, bảo mật, cache, đo hiệu năng — chúng cắt ngang mọi class ở mọi tầng, không thuộc về class nào cả. Thuật ngữ tiếng Anh là cross-cutting concern, tiếng Việt thường dịch là mối quan tâm xuyên suốt.

OOP gom code theo class, nên nó không có chỗ nào để đặt những thứ này. Đó chính là khoảng trống mà AOP lấp vào — vì vậy nói AOP bổ sung cho OOP chứ không thay thế.

1.3 · Ý tưởng của AOP

Aspect-Oriented Programming (AOP) là cách tách những logic xuất hiện ở nhiều nơi khỏi logic nghiệp vụ chính. Những logic như logging, transaction hoặc một số yêu cầu bảo mật thường được gọi là cross-cutting concerns. citeturn0search1

Ví dụ, nếu muốn log thời gian chạy của nhiều method, bạn không cần chép đoạn start = ... và end = ... vào từng method. Bạn định nghĩa phần log một lần trong một aspect, dùng pointcut để chọn các method cần áp dụng và để Spring AOP thực thi advice thông qua proxy.

Mối liên hệ

Aspect chứa logic → Pointcut chọn nơi áp dụng → Advice quy định thời điểm chạy → Proxy đứng giữa caller và bean để thực thi advice. Spring AOP là AOP dựa trên proxy và chủ yếu hỗ trợ join point ở mức method execution. citeturn0search9turn0search12

3.4 · Aspect — nơi chứa phần cắt ngang

LoggingAspect.java 
package com.example.demo.aspect;

import org.aspectj.lang.JoinPoint;
import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.*;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Component;

import java.util.Arrays;

@Aspect // ① class này chứa advice
@Component // ② VÀ nó phải là một bean — thiếu dòng này là không chạy
public class LoggingAspect {

 private static final Logger log = LoggerFactory.getLogger(LoggingAspect.class);

 // ③ POINTCUT — đặt tên cho một biểu thức để tái sử dụng
 @Pointcut("execution(* com.example.demo.service.*.*(..))")
 public void serviceMethods() { } // thân method luôn rỗng

 // ④ ADVICE — chạy TRƯỚC method
 @Before("serviceMethods()")
 public void logBefore(JoinPoint jp) {
 log.info("[Before] {}() tham số {}",
 jp.getSignature().getName(), Arrays.toString(jp.getArgs()));
 }

 // ⑤ chạy SAU khi method trả về bình thường — lấy được giá trị trả về
 @AfterReturning(pointcut = "serviceMethods()", returning = "result")
 public void logAfterReturning(JoinPoint jp, Object result) {
 log.info("[AfterReturning] {}() trả về {}",
 jp.getSignature().getName(), result);
 }

 // ⑥ chạy khi method NÉM EXCEPTION
 @AfterThrowing(pointcut = "serviceMethods()", throwing = "ex")
 public void logAfterThrowing(JoinPoint jp, Exception ex) {
 log.error("[AfterThrowing] {}() ném {}: {}",
 jp.getSignature().getName(), ex.getClass().getSimpleName(), ex.getMessage());
 }

 // ⑦ LUÔN chạy, thành công hay lỗi — giống finally
 @After("serviceMethods()")
 public void logAfter(JoinPoint jp) {
 log.info("[After] {}() kết thúc", jp.getSignature().getName());
 }

 // ⑧ BAO TRỌN method — tự quyết có gọi tiếp hay không
 @Around("serviceMethods()")
 public Object measureTime(ProceedingJoinPoint pjp) throws Throwable {
 long start = System.currentTimeMillis();
 log.info("[Around] vào {}()", pjp.getSignature().getName());
 try {
 return pjp.proceed(); // ← gọi method thật
 } finally {
 log.info("[Around] ra {}() — {} ms",
 pjp.getSignature().getName(), System.currentTimeMillis() - start);
 }
 }
}

5.3 · @Around khác hẳn bốn cái kia

Bốn advice đầu chỉ quan sát. @Around thì cầm quyền thiết lập: nó quyết định có gọi method thật hay không, có sửa tham số không, có sửa giá trị trả về không.

ba việc chỉ @Around làm được 
// ① Không gọi method thật — ví dụ cache
@Around("@annotation(Cacheable)")
public Object cache(ProceedingJoinPoint pjp) throws Throwable {
 String key = pjp.getSignature().getName() + Arrays.toString(pjp.getArgs());
 if (store.containsKey(key)) {
 return store.get(key); // ← method THẬT không chạy
 }
 Object result = pjp.proceed();
 store.put(key, result);
 return result;
}

// ② Sửa tham số trước khi gọi
Object[] args = pjp.getArgs();
args[0] = ((String) args[0]).trim();
return pjp.proceed(args); // truyền tham số đã sửa

// ③ Gọi lại khi lỗi — retry
for (int i = 0; i < 3; i++) {
 try { return pjp.proceed(); }
 catch (Exception e) { if (i == 2) throw e; }
}
Quên proceed() là hỏng ngầm

@Around không gọi proceed() thì method gốc không bao giờ chạy. Advice trả về null (hoặc giá trị bạn trả), và không có lỗi nào được ném ra.

Triệu chứng: API trả về null, dữ liệu không được lưu, mà log sạch sẽ không báo gì. Đây là bug tốn thời gian nhất của AOP.

9.1 · JdbcTemplate giải quyết vấn đề gì

package com.example.demo.repository;

import com.example.demo.model.Employee;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.core.RowMapper;
import org.springframework.stereotype.Repository;

import java.util.List;

@Repository
public class EmployeeDao {

 private final JdbcTemplate jdbc;

 public EmployeeDao(JdbcTemplate jdbc) { // Spring Boot đã tạo sẵn bean này
 this.jdbc = jdbc;
 }

 // map MỘT DÒNG của ResultSet thành MỘT object
 private final RowMapper<Employee> mapper = (rs, rowNum) -> new Employee(
 rs.getLong("id"),
 rs.getString("name"),
 rs.getString("email"));

 // ① query — trả về NHIỀU dòng
 public List<Employee> findAll() {
 return jdbc.query("SELECT id, name, email FROM employee ORDER BY id", mapper);
 }

 // ② queryForObject — trả về ĐÚNG MỘT dòng
 public Employee findById(long id) {
 return jdbc.queryForObject(
 "SELECT id, name, email FROM employee WHERE id = ?", mapper, id);
 }

 // ③ queryForObject với kiểu đơn — đếm, tính tổng
 public int count() {
 Integer n = jdbc.queryForObject("SELECT COUNT(*) FROM employee", Integer.class);
 return n == null ? 0 : n;
 }

 // ④ update — dùng cho INSERT, UPDATE và DELETE; trả về SỐ DÒNG bị ảnh hưởng
 public int insert(Employee e) {
 return jdbc.update(
 "INSERT INTO employee(name, email) VALUES (?, ?)",
 e.getName(), e.getEmail());
 }

 public int updateEmail(long id, String email) {
 return jdbc.update("UPDATE employee SET email = ? WHERE id = ?", email, id);
 }

 public int deleteById(long id) {
 return jdbc.update("DELETE FROM employee WHERE id = ?", id);
 }

 // ⑤ tìm kiếm — chú ý dấu % nằm ở THAM SỐ, không nằm trong câu SQL
 public List<Employee> searchByName(String keyword) {
 return jdbc.query(
 "SELECT id, name, email FROM employee WHERE LOWER(name) LIKE LOWER(?)",
 mapper, "%" + keyword + "%");
 }
}

Luyện tập

Bài tập ôn tập

Bốn bài đầu cho AOP, ba bài sau cho JdbcTemplate. Gợi ý nằm trong phần mở ra được.

AOP 1. Viết một aspect in ra thời gian chạy của mọi method trong package service. Gọi thử một API và xem log.

Dùng @Around — bốn advice còn lại không đo được thời gian vì chúng không “bao” lấy method.

@Around("execution(* com.example.demo.service.*.*(..))")
public Object measure(ProceedingJoinPoint pjp) throws Throwable {
 long t = System.currentTimeMillis();
 try { return pjp.proceed(); }
 finally { log.info("{} mất {} ms", pjp.getSignature().getName(),
 System.currentTimeMillis() - t); }
}
AOP 2. Bỏ @Component khỏi aspect rồi chạy lại. Chuyện gì xảy ra, và vì sao không có lỗi nào báo?

Advice ngừng chạy hoàn toàn, log im lặng, ứng dụng vẫn hoạt động bình thường. Không có lỗi vì với Spring, class đó đơn giản là không tồn tại — nó không được component scan nhận nên không bao giờ được xem xét.

Đây là lý do khi AOP “không chạy”, việc đầu tiên cần kiểm tra là aspect đã có @Component chưa.

AOP 3. Tự tái hiện bẫy self-invocation: viết outer() gọi inner() trong cùng class, cả hai đều khớp pointcut. Chứng minh advice của inner() không chạy, rồi sửa cho nó chạy.

Gọi outer() từ controller, xem log: chỉ thấy advice của outer(). Thêm một System.out.println("inner") bên trong inner() để chắc chắn method vẫn chạy — chỉ là advice bị bỏ qua.

Sửa: tách inner() sang một @Service khác rồi inject vào. Đây là cách gỡ tốt nhất, vì nó buộc bạn chia trách nhiệm rõ ràng hơn.

Làm xong bài này, bạn đã hiểu trước một nửa Spring Boot Bài 7 — @Transactional dính đúng bẫy này.

AOP 4. Tạo annotation @Audited của riêng bạn, viết aspect khớp theo nó, và gắn vào đúng một method. Kiểm tra: method không gắn thì không bị advice.

Nhớ @Retention(RetentionPolicy.RUNTIME) — thiếu nó thì annotation bị xoá khi biên dịch, reflection không đọc được, và aspect sẽ không bao giờ khớp. Đây là lỗi im lặng khó tìm.

Tóm tắt

Ôn lại trước khi sang Spring Data JPA

1. AOP giải quyết vấn đề gì mà OOP không giải được?

Cross-cutting concern — những việc cắt ngang mọi class ở mọi tầng (log, transaction, bảo mật, cache). OOP gom code theo class nên không có chỗ đặt chúng; viết tay thì lặp, khó sửa và dễ quên.

2. Phân biệt pointcut, advice, aspect, join point.

Pointcut = ở đâu. Advice = làm gì. Aspect = class gom cả hai. Join point = điểm cụ thể được áp (với Spring luôn là một lời gọi method).

3. Đọc biểu thức execution(* com.example.service.*.*(..)).

Mọi method (* thứ hai), của mọi class (* thứ nhất sau package), trong package com.example.service, kiểu trả về bất kỳ (* đầu), tham số bao nhiêu cũng được (..).

4. Năm loại advice, cái nào luôn chạy kể cả khi lỗi?

@After (giống finally) và @Around — nếu phần sau proceed() nằm trong khối finally. @AfterReturning chỉ chạy khi thành công, @AfterThrowing chỉ chạy khi có exception.

5. Vì sao @Around mạnh hơn bốn cái kia?

Vì nó cầm quyền thiết lập: quyết định có gọi method thật không (proceed()), sửa được tham số đầu vào, sửa được giá trị trả về, và gọi lại được nhiều lần. Bốn cái kia chỉ quan sát.

6. Spring chèn advice vào bằng cách nào?

Bằng proxy: lúc khởi động, container đưa cho nơi cần một object trung gian bọc quanh bean gốc, thay vì đưa bean gốc. Advice chạy trong proxy. Spring Boot mặc định dùng CGLIB (tạo class con).

7. Ba trường hợp advice không chạy dù đã viết đúng?

① Self-invocation — gọi method trong cùng class, không qua proxy. ② Method không phải public (hoặc là static/final). ③ Aspect thiếu @Component nên không phải bean. Cả ba đều im lặng, không báo lỗi.

8. Vì sao hiểu proxy lại quan trọng cho @Transactional?

Vì @Transactional chính là AOP. Method @Transactional gọi từ method khác trong cùng class thì transaction không được mở — cùng bẫy self-invocation. @Async, @Cacheable, @PreAuthorize cũng vậy.

9. JdbcTemplate làm hộ bạn bốn việc gì?

Mở/đóng connection, đóng Statement và ResultSet (kể cả khi lỗi), dịch SQLException thành DataAccessException unchecked, và gán tham số cho PreparedStatement.

10. queryForObject khi không tìm thấy dòng nào thì trả về gì?

Không trả về gì cả — nó ném EmptyResultDataAccessException. Muốn an toàn thì dùng query() rồi .stream().findFirst() để có Optional.

11. Vì sao phải dùng dấu ? thay vì nối chuỗi vào câu SQL?

Chống SQL injection. Với placeholder, giá trị được gửi xuống database tách rời khỏi câu lệnh nên không thể đổi nghĩa câu SQL. Nối chuỗi thì dữ liệu người dùng trở thành một phần câu lệnh.

Xong Spring Core

Ba bài của phần Core đã trọn: ai tạo object (Bài 1 — container, bean, DI), xử lý việc cắt ngang (Bài 2 — AOP và proxy), chạm tay vào database (Bài 3 — Maven và JdbcTemplate).

Phần Spring Data JPA tiếp theo xây thẳng lên cả ba: repository là bean do container tạo, @Transactional là AOP chạy bằng proxy, và toàn bộ nó tồn tại để bạn không phải viết lại cái EmployeeDao ở mục 9.3.

9.2 · Bên sở hữu — khái niệm cần nắm rõ nhất

Trong database, quan hệ một–nhiều chỉ có một cột khóa ngoại. Nhưng trong Java bạn có thể khai ở cả hai class. Vậy Hibernate phải biết: bên nào thật sự thiết lập cột khóa ngoại đó?

Quy tắc: bên nào có @JoinColumn thì bên đó sở hữu. Bên kia khai mappedBy để nói “tôi chỉ là ảnh phản chiếu”.

@Entity
@Table(name = "department")
public class Department {

 @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
 private Long id;

 private String name;

 // BÊN PHẢN CHIẾU — không có @JoinColumn, có mappedBy
 @OneToMany(mappedBy = "department", // ← tên FIELD ở class Employee
 cascade = CascadeType.ALL,
 fetch = FetchType.LAZY, // đoạn này ghi "workspace =" → sai
 orphanRemoval = true)
 private List<Employee> employees = new ArrayList<>();
}

@Entity
@Table(name = "employee")
public class Employee {

 @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
 private Long id;

 private String name;

 // BÊN SỞ HỮU — có @JoinColumn, tức là giữ cột khóa ngoại
 @ManyToOne(fetch = FetchType.LAZY) // đổi khỏi EAGER mặc định
 @JoinColumn(name = "department_id")
 private Department department;
}

Hibernate chỉ nhìn vào bên sở hữu khi sinh câu SQL. Bên mappedBy tồn tại để bạn đọc cho tiện, nó không thiết lập gì cả.

11.3 · Locking

Vấn đề Lost Update: hai người cùng đọc một bản ghi, A sửa xong, B sửa đè lên mà không biết thay đổi của A.

OptimisticPessimistic
Giả địnhXung đột hiếmXung đột hay xảy ra
Cách làmThêm field @Version, so version lúc updateKhóa dòng ngay lúc đọc
Khi xung độtNém ObjectOptimisticLockingFailureExceptionTransaction kia phải chờ
Chi phíRẻ, không giữ khoá ở DBĐắt, dễ nghẽn và deadlock

optimistic — chỉ cần một field 
@Entity
public class Product {
 @Version
 private Long version; // Hibernate tự tăng mỗi lần UPDATE
}

// Câu SQL Hibernate sinh ra:
// UPDATE product SET ..., version = 4 WHERE id = ? AND version = 3
// Ai đó đã sửa trước → version không còn là 3 → 0 dòng bị ảnh hưởng → ném exception
public interface ProductRepository extends JpaRepository<Product, Long> {

 @Override
 @Lock(LockModeType.PESSIMISTIC_WRITE)
 Optional<Product> findById(Long id);
}

@Lock chỉ có tác dụng bên trong một transaction đang mở. Ba mode về nội dung: PESSIMISTIC_READ, PESSIMISTIC_WRITE, PESSIMISTIC_FORCE_INCREMENT.

Chọn cái nào

Mặc định nên là optimistic — thêm một field @Version gần như miễn phí và đủ cho hầu hết trường hợp. Chỉ dùng pessimistic khi thật sự có tranh chấp cao và mất mát là nghiêm trọng: trừ tồn kho, đặt vé, chuyển tiền.

Điều đáng nhớ: lỗi này xảy ra lúc khởi động, trước khi có request nào. So với JdbcTemplate — gõ sai tên cột trong câu SQL thì mãi tới lúc gọi API mới biết.

Tóm tắt

Ôn lại trước khi sang Spring Boot

1. Phân biệt JDBC, JPA, Hibernate, Spring Data JPA trong một câu.

JDBC là API mức thấp; JPA là đặc tả (chỉ interface); Hibernate là bản cài đặt của JPA; Spring Data JPA là lớp trên sinh sẵn repository. Một dependency spring-boot-starter-data-jpa mang cả bốn.

2. Vì sao JpaRepository không cần class cài đặt?

Spring Data sinh implementation lúc chạy bằng proxy, dựa trên tên method và kiểu entity bạn khai trong generic. Cùng cơ chế proxy đã học ở phần AOP.

3. ddl-auto=update sai ở chỗ nào với production?

Nó chỉ thêm, không sửa kiểu cột, không xoá, không đổi tên — nên schema thật sẽ khác thứ bạn nghĩ. Không có lịch sử, không rollback được. Production dùng validate + Flyway/Liquibase.

4. Tên method sai một chữ thì lỗi lộ ra lúc nào?

Lúc khởi động, với PropertyReferenceException kèm gợi ý tên đúng. Compile vẫn qua vì đó chỉ là một khai báo trong interface.

5. JPQL và native query khác nhau chỗ nào?

JPQL viết theo tên class và field, không phụ thuộc database. Native viết theo tên bảng và cột, dùng được hàm riêng của DB nhưng đổi database có thể phải sửa.

6. Ba annotation phải đi cùng nhau khi viết query UPDATE?

@Modifying + @Transactional + @Query. Nên thêm clearAutomatically = true vì query kiểu này đi thẳng xuống DB, không qua persistence context.

7. Trong quan hệ hai chiều, bên nào thiết lập cột khóa ngoại?

Bên có @JoinColumn — tức bên @ManyToOne. Bên mappedBy chỉ để đọc. Chỉ set bên mappedBy thì dữ liệu không lưu, và không có lỗi nào báo.

8. Fetch mặc định của @ManyToOne là gì, nên đổi không?

EAGER (cùng với @OneToOne). Nên đổi hết sang FetchType.LAZY rồi chủ động nạp khi cần bằng @EntityGraph hoặc join fetch.

9. N+1 là gì, phát hiện và chữa thế nào?

Lấy N bản ghi rồi lặp đụng vào quan hệ LAZY → 1 + N câu query. Phát hiện: bật show-sql, đếm câu query lặp lại. Chữa: @EntityGraph(attributePaths=...) hoặc join fetch.

10. Vì sao không nên trả entity thẳng ra API?

Ba lý do: LazyInitializationException khi Jackson đụng quan hệ LAZY ngoài transaction; JSON lặp vô hạn với quan hệ hai chiều; và lộ field không nên lộ. Dùng DTO chữa cả ba.

11. Optimistic và pessimistic lock, mặc định nên chọn gì?

Optimistic — chỉ cần thêm field @Version, rẻ, không giữ khoá ở DB. Pessimistic (@Lock) chỉ dùng khi tranh chấp cao và hậu quả nghiêm trọng: tồn kho, đặt chỗ, chuyển tiền.

Xong Spring Data JPA

Phần Spring Boot tiếp theo không thêm cách truy cập dữ liệu nào mới — nó xây lên đúng những gì bạn vừa học. Ở Bài 5, ResourceNotFoundException bạn ném từ orElseThrow sẽ được @ControllerAdvice bắt và chuyển thành HTTP 404. Ở Bài 7, @Transactional được mổ xẻ đầy đủ. Ở Mini Project, chính hai entity Employee và Department này là bài tập chính.

Ba thứ nên mang theo: entity không ra khỏi service, quan hệ để LAZY rồi nạp chủ động, và luôn bật show-sql khi phát triển.

Sáu mục tiêu: annotation là gì, nhóm core, nhóm xử lý request, nhóm khác, nhóm test, và nhóm nâng cao. Bài này là bản mục lục của cả khoá — bảng tra cứu đầy đủ nằm ở Phụ lục A.

1 · Annotation là gì

Annotation là metadata — dữ liệu mô tả dữ liệu — đặt trên class, method hoặc biến, bắt đầu bằng @. Tự thân nó không làm thay đổi việc biên dịch hay chạy chương trình; tác dụng đến từ thứ đọc nó — ở đây là Spring lúc khởi động.

Mối liên hệ với BootProperties là nguồn cấu hình cho ứng dụng: database, server, logging, profile... Spring Boot đọc các giá trị này và bind chúng vào cấu hình hoặc bean. Vì vậy phần này nên được hiểu sau khi đã biết Boot khởi động và auto-configuration hoạt động như thế nào.

Bốn mục tiêu: giới thiệu, cấu trúc file, các property hay dùng, và quản lý cấu hình theo môi trường bằng profile.

Bổ sung — thứ tự ưu tiên và relaxed binding

Nếu một khóa xuất hiện ở nhiều nơi, Spring Boot lấy theo thứ tự ưu tiên giảm dần: tham số dòng lệnh → biến môi trường → application-{profile}.yml → application.yml. Vì vậy deploy không cần sửa file, chỉ cần đặt biến môi trường.

Relaxed binding: spring.datasource.url cũng nhận được từ biến môi trường SPRING_DATASOURCE_URL. Quy tắc: chữ hoa, dấu chấm và gạch ngang thành gạch dưới.

Nội dung này về property trong parent–child context của Spring MVC cổ điển: file khai ở parent thì cả hai context đều đọc được; khai ở child thì parent không thấy. Với Spring Boot chỉ có một context nên tình huống này gần như không gặp.

Handle Exception

Mối liên hệ với RESTException handling nằm giữa service và HTTP response. Service có thể ném exception mang ý nghĩa nghiệp vụ; tầng web quyết định cách biến exception đó thành HTTP status và error body. @ControllerAdvice giúp gom cách xử lý này về một chỗ.

Tám mục tiêu: các cơ chế xử lý lỗi, xử lý cục bộ, xử lý toàn cục, tích hợp validation, custom exception, cấu trúc error response, thứ tự ưu tiên, và best practice. Bài dài thứ hai của khoá.

public class ExampleController {

Spring Security

Mối liên hệ với requestSecurity nằm trước và quanh luồng xử lý controller. Request đi qua security filter chain trước khi vào controller; authentication xác định “ai đang gọi”, authorization quyết định “người đó được phép làm gì”.

Bảy mục tiêu: giới thiệu, kiến trúc lõi, cấu hình, xác thực, phân quyền, authorization filter, và method security.

1 · Spring Security là gì

Framework chuyên về authentication (bạn là ai) và authorization (bạn được làm gì) cho ứng dụng Java. Không phải một thư viện đơn lẻ mà là một hệ sinh thái module. Tính năng chính về nội dung: xác thực, phân quyền, chống CSRF, bảo vệ session, hỗ trợ REST API, tích hợp với công nghệ khác.

Không bao giờ lưu mật khẩu dạng thô

BCrypt cố tình chậm và tự sinh salt cho từng mật khẩu — chính vì vậy nó chống được brute force và rainbow table. Băm là một chiều: không có cách “giải mã” ngược, chỉ có matches(). Tính năng “quên mật khẩu” vì thế phải là đặt lại mật khẩu, không phải gửi lại mật khẩu cũ.

4 · Cấu hình

Chỉ cần thêm spring-boot-starter-security, Spring Boot đã bật sẵn: chặn toàn bộ endpoint, form login, HTTP Basic, một user mặc định (in mật khẩu ra console), bảo vệ CSRF, và các security header. Muốn tuỳ biến thì tự khai bean SecurityFilterChain — khi đó cấu hình mặc định không áp dụng nữa.

@Configuration
@EnableWebSecurity
public class SecurityConfig {

 @Bean
 public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
 http
 .authorizeHttpRequests(auth -> auth
 .requestMatchers("/css/**", "/js/**", "/public/**").permitAll()
 .requestMatchers("/", "/home").permitAll()
 .requestMatchers("/admin/**").hasRole("ADMIN")
 .requestMatchers("/products/**").hasAuthority("product:read")
 .requestMatchers(HttpMethod.POST, "/products").hasAuthority("product:write")
 .anyRequest().authenticated() // ← luôn để cuối cùng
 )
 .formLogin(Customizer.withDefaults())
 .httpBasic(Customizer.withDefaults());

 return http.build();
 }
}
Thứ tự matcher rất quan trọng

Spring duyệt từ trên xuống và dừng ở dòng khớp đầu tiên. Đặt anyRequest() lên trên là mọi dòng dưới thành vô nghĩa. Quy tắc: cụ thể trước, tổng quát sau.

Bẫy số một của Spring Security — tiền tố ROLE_

hasRole("ADMIN") thực chất đi tìm authority tên ROLE_ADMIN — nó tự thêm tiền tố. hasAuthority("ADMIN") thì tìm đúng chuỗi ADMIN. Nếu trong DB bạn lưu role là "ADMIN" mà lại kiểm tra bằng hasRole("ADMIN"), kết quả luôn là 403 — và không có thông báo nào giải thích vì sao.

Chọn một trong hai: lưu ROLE_ADMIN trong DB và dùng hasRole("ADMIN"), hoặc lưu ADMIN và dùng hasAuthority("ADMIN").

Transaction Management

Mối liên hệ với Data AccessTransaction thường bao quanh một use case nghiệp vụ có nhiều thao tác database. Vì vậy @Transactional thường đặt ở service boundary thay vì rải transaction tùy ý ở từng repository method.

Sáu mục tiêu: transaction là gì, lớp trừu tượng của Spring, cấu hình, các thuộc tính của @Transactional, cơ chế hoạt động, và rollback.

1 · Transaction là gì

Một đơn vị công việc logic gồm một hoặc nhiều thao tác, được coi là khối không thể chia: hoặc thành công hết (commit), hoặc thất bại hết và quay về trạng thái ban đầu (rollback). Mục đích: giữ toàn vẹn và nhất quán dữ liệu.

Hai cách quản lý: programmatic (gọi API trực tiếp, hoặc TransactionTemplate) và declarative (dùng @Transactional — cách được chọn trong hầu hết trường hợp).

2 · Lớp trừu tượng của Spring

Interface trung tâm là PlatformTransactionManager với ba thao tác: getTransaction(), commit(), rollback(). Bạn hầu như không gọi trực tiếp — @Transactional làm hộ. Lợi ích: code nghiệp vụ không dính API của JDBC hay JPA, đổi công nghệ truy cập dữ liệu gần như không phải sửa gì.

3 · Đặt @Transactional ở đâu

Đặt trênPhạm vi
ClassMọi method public của class đó (và class con)
MethodChỉ method đó — ghi đè cấu hình ở mức class
 
@Service
@Transactional(readOnly = true)
public class ReportService {

 public Report generateDailyReport() {
 // chạy trong transaction chỉ đọc, thừa kế từ class
 }

 @Transactional(readOnly = false, noRollbackFor = FileNotFoundException.class)
 public void archiveOldReport(Long reportId) throws FileNotFoundException {
 // transaction ghi; lỗi khác vẫn rollback bình thường
 }
}
— hai giới hạn phải thuộc lòng

Self-invocation. Method @Transactional gọi một method @Transactional khác trong cùng class thì lời gọi không đi qua proxy → transaction mới không được áp dụng. Muốn đúng thì tách sang bean khác, hoặc tự inject chính mình (@Lazy), hoặc dùng TransactionTemplate.

Chỉ method public. Đặt @Transactional trên method private hoặc protected thì nó bị bỏ qua lặng lẽ — không có cảnh báo nào.

4 · Propagation

Quy định một method có transaction sẽ ứng xử thế nào khi gọi từ trong một transaction khác.

6 · Rollback

Method némSpring làm gì

Checked Exception (IOException, SQLException…)COMMIT — đây là chỗ hay gây bất ngờ
 
class InsufficientFundsException extends Exception { } // checked
class MinorDataWarningException extends RuntimeException { } // unchecked

@Service
public class AccountService {

 // checked exception này cũng phải rollback → khai rollbackFor
 @Transactional(rollbackFor = InsufficientFundsException.class)
 public void transferFunds(String from, String to, double amount)
 throws InsufficientFundsException { ... }

 // cảnh báo nhỏ, KHÔNG muốn huỷ cả transaction → noRollbackFor
 @Transactional(noRollbackFor = MinorDataWarningException.class)
 public void updateAccountDetails(AccountDetails details) { ... }
}
— cái bẫy nguy hiểm nhất của cả bài

Bắt một RuntimeException bên trong method @Transactional mà không ném lại thì Spring không biết có lỗi và sẽ commit — dữ liệu hỏng một nửa mà không ai hay.

Hai cách xử lý đúng: ném lại (chính exception đó hoặc một RuntimeException khác), hoặc đánh dấu thủ công: TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();

lưu thêm: dù transaction có rollback hay không, exception vẫn tiếp tục lan lên tầng gọi (thường là Controller, rồi tới @ControllerAdvice ở Bài 5) — trừ khi bạn bắt nó bên trong.

Working with Thymeleaf

Mối liên hệ với Spring MVCThymeleaf là view layer cho ứng dụng server-side rendering. Controller đưa model vào view, Thymeleaf dùng model đó để tạo HTML trả về trình duyệt. Nó không thay thế Service, Repository hay Security; nó chỉ phụ trách phần giao diện server-side.

Tám mục tiêu: giới thiệu, cú pháp cơ bản, link động, điều kiện & vòng lặp, form, validation, fragment, và tích hợp sâu với Spring. Bài dài nhất khoá — và là bài gần với công việc frontend nhất.

1 · Thymeleaf là gì

Template engine chạy phía server: xử lý file HTML trên server, chèn dữ liệu, lặp, rẽ nhánh, rồi mới gửi HTML hoàn chỉnh về trình duyệt. Trong hệ sinh thái Spring, đây là lựa chọn số một cho tầng View.

Quy ước mặc định của Spring Boot: template nằm ở src/main/resources/templates/, đuôi .html, content-type text/html, encoding UTF-8. File tĩnh (css, js, ảnh) ở src/main/resources/static/.

Hệ quả: không có state phía client, mỗi thao tác là một request mới và cả trang được dựng lại. Đổi lại, không cần build, không có hydration, SEO tự nhiên. 18 câu qua cả ba phần

Trả lời trong đầu trước, rồi bấm để mở đáp án.

Core 1. Bean scope mặc định là gì, và vì sao không được để state của request trong field của @Service?

singleton. Một bản duy nhất cho cả container, dùng chung cho mọi request. Java xử lý request bằng nhiều thread thật, nên hai request đồng thời sẽ ghi đè lên field của nhau. Đây là loại lỗi Node không có vì chỉ một luồng.

Core 1. Hai class cùng implement PaymentGateway, @Autowired báo lỗi gì và chữa thế nào?

NoUniqueBeanDefinitionException. Chữa bằng @Primary trên bean mặc định, hoặc @Qualifier("tênBean") tại chỗ inject.

Core 1. Vì sao nên constructor injection hơn field injection?

Ba lý do. Field khai được final nên bất biến; thiếu dependency thì lỗi ngay lúc khởi động chứ không NullPointerException lúc chạy; và test viết được bằng new Service(mockRepo) mà không cần khung Spring.

Core 2. Method a() gọi b() trong cùng class, b() có @Transactional. Transaction có được mở không?

Không. Self-invocation không đi qua proxy nên advice bị bỏ qua hoàn toàn — và không có cảnh báo nào. Cùng nguyên nhân với @Async, @Cacheable, @PreAuthorize khi bị gọi nội bộ.

Core 2. Viết @Around mà quên proceed() thì chuyện gì xảy ra?

Method gốc không chạy. Advice trả về null (hoặc giá trị bạn trả), chương trình không báo lỗi gì cả — rất khó tìm ra.

JPA 1. Phân biệt JPA, Hibernate và Spring Data JPA trong một câu.

JPA là đặc tả, Hibernate là bản cài đặt, Spring Data JPA là lớp trên sinh sẵn repository. Thêm spring-boot-starter-data-jpa là có cả ba, mặc định Hibernate.

JPA 2. findByUserName nhưng entity chỉ có field username — lỗi lộ ra lúc nào?

Lúc khởi động ứng dụng, với PropertyReferenceException: No property 'userName' found. Compile vẫn qua vì đó chỉ là một khai báo method trong interface.

JPA 2. Lấy 100 User rồi lặp gọi user.getPosts() — bao nhiêu câu query, và chữa thế nào?

101 câu — đây là N+1. Chữa bằng @EntityGraph(attributePaths = "posts") trên method repository, hoặc @Query("select u from User u join fetch u.posts").

JPA 2. Fetch mặc định của @ManyToOne là gì?

EAGER — và @OneToOne cũng vậy. Ngược lại, @OneToMany và @ManyToMany mặc định LAZY. Thực tế nên đặt tất cả về FetchType.LAZY rồi chủ động fetch khi cần.

Boot 1. Khi nào trả 401, khi nào 403?

401 = chưa xác thực (chưa đăng nhập, token hết hạn hoặc sai). 403 = đã xác thực nhưng không đủ quyền. Dùng lẫn hai mã này làm frontend xử lý sai: 401 thì nên đưa về trang đăng nhập, 403 thì chỉ nên báo không có quyền.

Boot 2. @SpringBootApplication gồm những annotation nào?

@SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan. Vì có @ComponentScan nên class này phải nằm ở package gốc — bean nằm ngoài cây package đó sẽ không được tìm thấy.

Boot 3. @RequestParam String name mà request không gửi name thì sao?

400 Bad Request, không phải null. Muốn tuỳ chọn thì khai required = false hoặc defaultValue. Khác hẳn req.query.name của Express.

Boot 4. Cùng một khoá có ở dòng lệnh, biến môi trường và application.yml — cái nào thắng?

Tham số dòng lệnh, rồi biến môi trường, rồi application-{profile}.yml, cuối cùng là application.yml. Nhờ vậy deploy chỉ cần đổi biến môi trường, không phải sửa file.

Boot 5. ErrorResponse có đủ field nhưng client nhận {} — vì sao?

Thiếu getter. Jackson serialize theo getter, không đọc field private trực tiếp. Thêm getter, dùng Lombok @Getter, hoặc chuyển sang record.

Boot 6. DB lưu role là "ADMIN", code kiểm tra hasRole("ADMIN") — kết quả?

Luôn 403. hasRole("ADMIN") tự thêm tiền tố và đi tìm authority ROLE_ADMIN. Hoặc lưu ROLE_ADMIN trong DB, hoặc đổi sang hasAuthority("ADMIN").

Boot 7. Method @Transactional ném IOException (checked) — commit hay rollback?

Commit. Mặc định Spring chỉ rollback với RuntimeException và Error. Muốn rollback với checked exception phải khai @Transactional(rollbackFor = IOException.class).

Boot 7. Bắt RuntimeException trong method @Transactional rồi chỉ log, không ném lại — hậu quả?

Transaction được commit với dữ liệu hỏng một nửa, vì Spring không hề biết có lỗi. Phải ném lại, hoặc gọi TransactionAspectSupport.currentTransactionStatus().setRollbackOnly().

Boot 8. Khi nào dùng th:text, khi nào th:utext?

Mặc định luôn th:text — nó escape HTML nên chặn XSS. th:utext chỉ dùng cho HTML do chính hệ thống sinh ra và đã làm sạch; với dữ liệu người dùng nhập thì đó là lỗ hổng XSS, đúng vai trò của dangerouslySetInnerHTML bên React.
